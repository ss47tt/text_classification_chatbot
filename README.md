# Customer Service Agent — Bitext DeBERTa → Llama → SQL

A local, agentic customer-service chatbot built as a [LangGraph](https://github.com/langchain-ai/langgraph)
state machine. A fine-tuned DeBERTa classifier routes each customer message
by intent; simple requests get a direct conversational reply from a local
Llama model, while data-lookup requests are turned into SQL, validated,
executed against a SQLite database, and summarised back to the customer.

---

## Architecture

```
Customer message
      │
      ▼
┌──────────────────────┐
│  Input Validation     │  Layer 1: non-ASCII check (catches 我问为什么)
│                       │  Layer 2a: pyenchant dictionary check
│                       │  Layer 2b: pinyin syllable fallback (wo bu zhi dao…)
└──────────┬────────────┘
           │ non-English / gibberish
           ▼
      handle_error ──────────────────────────────────────────► END
           │
           │ valid English
           ▼
┌──────────────────────┐
│  Keyword Override     │  Fast pattern match before DeBERTa
│  (18 intents mapped)  │  e.g. "where is my" → track_order
└──────────┬────────────┘
           │ no keyword match
           ▼
┌──────────────────────┐
│  classify_intent      │  DeBERTa (fine-tuned on Bitext, 27 intents)
└──────────┬────────────┘
           │
     confidence < 0.5 ──────────────────────────────────────► handle_error ──► END
           │
     needs_sql? ──── no ────────────────────────────────────► generate_response ──► END
           │
          yes
           ▼
┌──────────────────────┐
│  generate_sql         │  Priority 1: verified SQL template (no Llama)
│                       │  Priority 2: Llama fallback (unknown intents only)
└──────────┬────────────┘
           ▼
┌──────────────────────┐
│  validate_sql         │  Blocks DROP / DELETE / TRUNCATE / ALTER / UPDATE / INSERT
└──────────┬────────────┘
           ▼
┌──────────────────────┐
│  execute_sql          │  Runs query against customer_service.db
└──────────┬────────────┘
           │
     error + retries < 2 ──────────────────────────────────► back to generate_sql
           │
     no error / retries exhausted
           ▼
┌──────────────────────┐
│  generate_response    │  Llama summarises SQL result (or apologises on error)
│                       │  clean_response() strips prompt leaking from 3B model
└──────────┬────────────┘
           ▼
          END
```

## Repository structure

| File | Purpose |
|---|---|
| `deberta_bitext.py` | Fine-tunes `microsoft/deberta-v3-base` on the [Bitext customer-support dataset](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset) (27 intents). Saves to `./out/final_model`. |
| `init_db.py` | Creates and seeds `customer_service.db` — the SQLite database the agent queries. Safe to re-run (drops and recreates all tables). |
| `agent_bitext.py` | The LangGraph agent: input validation, keyword override, intent classification, routing, SQL generation/validation/execution, and response generation. |
| `test_db.py` | Sanity-checks `customer_service.db` — prints schema and runs one sample query per SQL intent, without loading DeBERTa or Llama. |
| `check_db.py` | Prints the exact schema of `customer_service.db` with column names and types. Use this to verify DB structure. |
| `customer_service.db` | Generated by `init_db.py`. Not meant to be edited by hand. |

## Requirements

```bash
pip install langgraph langchain langchain-huggingface
pip install langchain-community sqlalchemy sqlparse
pip install langchain-ollama transformers torch
pip install datasets evaluate
pip install pyenchant          # optional — improves gibberish detection
```

> **Windows pyenchant note:** pyenchant requires the Enchant C library.
> Download the installer from https://pyenchant.github.io/pyenchant/install.html.
> If not installed, the agent falls back to pinyin syllable detection automatically.

You also need a local LLM runtime. Two options are wired into `agent_bitext.py`:

**Option A — Ollama (recommended, CPU-friendly)**
1. Install [Ollama](https://ollama.com)
2. `ollama pull llama3.2:3b`
3. Confirm the Ollama service is running before starting the agent:
   ```powershell
   netstat -ano | findstr 11434   # should show LISTENING
   ```

**Option B — HuggingFace `meta-llama/Llama-3.2-3B-Instruct` (needs a GPU)**
1. `pip install accelerate bitsandbytes`
2. `huggingface-cli login` and accept the Meta licence on HF Hub
3. In `agent_bitext.py`, swap:
   ```python
   llm = load_llama_ollama()       # comment this out
   llm = load_llama_huggingface()  # uncomment this
   ```

## Setup

Run these once, in order, from the project folder:

**1. Train the intent classifier**
```bash
python deberta_bitext.py
```
Downloads the Bitext dataset, fine-tunes DeBERTa for 3 epochs across 27 customer
service intents, evaluates on a held-out test split, and saves the model to
`./out/final_model`. Update `DEBERTA_PATH` at the top of `agent_bitext.py` to
point at that folder.

> **Note:** Until DeBERTa is retrained on Bitext data, `agent_bitext.py` uses
> keyword overrides as a primary router (see [Keyword Override](#keyword-override)
> below). The agent is functional before retraining, but classification accuracy
> will be lower for inputs that don't match a keyword pattern.

**2. Create the database**
```bash
python init_db.py
```
Creates `customer_service.db` with 12 tables seeded with sample data for 3 customers,
4 orders, and matching invoices, refunds, deliveries, and reviews.

**3. Run the agent**
```bash
python agent_bitext.py
```
Chat at the `Customer:` prompt. Type `quit` to exit.

## Input Validation

Every message passes through a two-layer guard before reaching DeBERTa:

| Layer | What it catches | Example |
|---|---|---|
| Layer 1 — ASCII check | Non-ASCII scripts (CJK, Arabic, Cyrillic) | `我问为什么` |
| Layer 2a — pyenchant dictionary | Non-English ASCII text (if pyenchant installed) | Any non-English romanised text |
| Layer 2b — pinyin syllable set | Romanised Mandarin pinyin (fallback) | `wo bu zhi dao ni zai jiang shen mo` |

Invalid input routes to `handle_error` with a language-specific message:
- Non-ASCII script → `"I currently only support English."`
- Gibberish / pinyin → `"I didn't recognise that as a customer service question."`

---

## Keyword Override

A pattern-matching layer runs **after** input validation but **before** DeBERTa.
If a keyword phrase clearly matches a known intent, DeBERTa is skipped entirely.
This is the primary router while DeBERTa is being retrained on Bitext data, and
acts as a reliable safety net afterwards.

18 intents are covered, including:

| Phrase example | Intent matched |
|---|---|
| `"where is my order"`, `"track my order"` | `track_order` |
| `"how much is"`, `"price of"` | `review_order` (product price lookup) |
| `"refund policy"`, `"can i return"` | `check_refund_policy` |
| `"payment failed"`, `"billing problem"` | `payment_issue` |
| `"forgot my password"`, `"reset my password"` | `recover_password` |
| `"i want a refund"`, `"money back"` | `get_refund` |

## SQL Templates

All SQL intents have pre-written, verified queries in `SQL_TEMPLATES`. These
**completely bypass Llama SQL generation** for known intents — eliminating
hallucinated column names, failed JOINs, and retry loops.

Llama is only asked to generate SQL for intents that have no template (rare edge
cases). If a template query fails, the agent skips retries and goes straight to
`generate_response` (a DB problem, not a SQL problem).

| Intent | Template queries |
|---|---|
| `track_order` | `orders` JOIN `deliveries` |
| `check_invoice`, `get_invoice` | `invoices` JOIN `orders` |
| `track_refund` | `refunds` JOIN `orders` |
| `check_refund_policy` | `refund_policy` |
| `check_payment_methods` | `payment_methods` WHERE `is_active = 1` |
| `check_cancellation_fee` | `cancellation_policy` |
| `delivery_options` | `delivery_options` |
| `delivery_period` | `deliveries` JOIN `orders` |
| `review` | `reviews` JOIN `orders` JOIN `customers` |
| `review_order` | `order_items` JOIN `orders` (product price lookup) |

## Testing

**Database only (fast, no models needed)**
```bash
python test_db.py
```
Prints the full schema and runs one representative query per SQL intent directly
against `customer_service.db`, bypassing DeBERTa and Llama entirely. Run this
first to isolate schema or data problems from model problems.

**Check DB schema**
```bash
python check_db.py
```
Prints each table's exact column names and types. Use this to verify `DB_SCHEMA`
in `agent_bitext.py` matches your actual database.

**End-to-end, through the running agent**

| Intent | Try typing |
|---|---|
| `track_order` | `"Where is my order?"` |
| `check_invoice` / `get_invoice` | `"Can I get a copy of my invoice?"` |
| `check_refund_policy` | `"What's your refund policy?"` |
| `track_refund` | `"What's the status of my refund?"` |
| `check_payment_methods` | `"What payment methods do you accept?"` |
| `check_cancellation_fee` | `"How much does it cost to cancel my order?"` |
| `delivery_options` | `"What delivery options do you offer?"` |
| `delivery_period` | `"How long will delivery take?"` |
| `review` | `"I want to leave a review for my order"` |
| `review_order` | `"How much is the Wireless Mouse?"` |

| Pinyin | `"wo bu zhi dao"` → gibberish error message |

Watch the console for:
- `[Input Guard]` — input validation result
- `[Keyword Override]` — keyword match (if any)
- `[DeBERTa] Intent: ... | SQL: True/False` — classification result
- `[SQL Template]` or `[SQL Llama]` — which SQL path was used
- `[SQL Executor] Result:` — raw DB output
- `[Llama Response]` — final response preview

## Intent taxonomy

The Bitext dataset defines 27 intents across 10 categories. This agent splits
them into two routing groups:

**SQL intents** (need a database lookup):
`track_order`, `check_invoice`, `get_invoice`, `check_refund_policy`,
`track_refund`, `check_payment_methods`, `check_cancellation_fee`,
`delivery_options`, `delivery_period`, `review`, `review_order`

**Chat intents** (handled conversationally, no DB lookup):
`cancel_order`, `change_order`, `place_order`, `get_refund`, `payment_issue`,
`complaint`, `contact_customer_service`, `contact_human_agent`, `create_account`,
`delete_account`, `edit_account`, `recover_password`, `registration_problems`,
`switch_account`, `change_shipping_address`, `set_up_shipping_address`,
`newsletter_subscription`

Below 50% classifier confidence, the agent skips routing and asks the customer
to rephrase.

## Known limitations

- **No customer identity / query scoping.** `AgentState` has no authenticated
  `customer_id`, so SQL queries return all customers' records, not just the
  caller's. Fine for local testing against seed data; a `customer_id` filter
  would need to be enforced server-side before handling real multi-customer data.

- **Llama 3.2-3B prompt leaking.** Small models sometimes repeat prompt
  instructions in their output. `clean_response()` in `agent_bitext.py` strips
  common leak patterns (`\nPlease respond`, `\nExample of`, `\nNote:`, etc.)
  before the response is shown to the customer. Upgrading to a larger model
  (8B+) eliminates this almost entirely.

- **Currency not stored in DB.** Prices in `order_items` are plain `REAL` values
  with no currency column. The response prompt tells Llama to use SGD ($), but
  this is a prompt instruction, not a DB constraint — a stronger model or an
  explicit currency column in the schema would be more reliable.

- **Prompt injection via customer message.** `generate_sql` blocks destructive
  DML keywords but doesn't constrain which tables or columns get queried. Unusual
  phrasing in a customer message could steer the Llama fallback toward unintended
  queries. SQL templates remove this risk for all covered intents.

- **Ollama connection errors on first run.** If `agent_bitext.py` fails with
  `ConnectError: ... target machine actively refused it`, the Ollama background
  service likely wasn't running — confirm it's listening on port `11434` and retry.
